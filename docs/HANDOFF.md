## Принятая архитектура (главное)

**Pi — «мозг» (control plane), роутер — «руки» (data plane).** На роутере только
движки (nfqws2, usque, xray) и маленький **nuxk-agent**; UI, кэш решений,
подбор стратегий, пресеты, история — на Pi. Pi выключен → роутер работает по
последнему пакету решений.

**Решение принимается в момент DNS, не при подключении.** После E0 (25.09)
выбран **native-режим**: nuxk ведёт встроенную маршрутизацию KeeneticOS по
доменам, а не строит свою.

```
Pi: решения домен → режим ──► nuxk-agent на роутере (RCI / ndmc)
   object-group fqdn nuxk-warp   ─► dns-proxy route ─► OpkgTun0 (usque)
   object-group fqdn nuxk-vless  ─► dns-proxy route ─► OpkgTun1 (xray)
   object-group fqdn nuxk-desync ─► список для nfqws2 (маршрута нет)
ndnproxy + ядро сами: ipset, метки (_NDM_DNSRT_*), таблицы (4096+)
```

Почему (факты E0 на Ultra NC-1812, KeeneticOS 5.01 preview):
- у пользователя уже работает встроенная маршрутизация по доменам —
  4 WG-списка, `_NDM_DNSRT_PREROUTING_MANGLE`, таблицы 4096–4099;
- её правила перезаписывают метку целиком (`--set-xmark …/0xffffffff`) —
  своих бит для меток фактически нет, а в native-режиме метки выделяет Keenetic;
- на :53 `ndnproxy` с DoH (Google, Cloudflare) и профилем `DnsProfile0`
  (xbox-dns) — DNS пользователя **не трогаем**; «мягкий режим» с агентом на
  `127.0.0.1:5300` отменён, остаётся только для бэкенда `linux`.

Решения по дизайну:
1. **Два бэкенда агента, один интерфейс для Pi:** `keenetic` (объекты ndm) —
   основной; `linux` (свой резолвер + ipset + свои метки) — стенд на Pi и
   роутеры без этой функции.
2. **WG не цель маршрута — Horizon его заменяет.** Сейчас WG-списки
   пользователя проксируют домены через VPN; эту работу забирает Horizon
   (режимы десинк / WARP / VLESS). Пользователь перенесёт домены в Horizon
   (импорт как решения «вручную»), затем WG-маршруты выключаются.
   Миграция по одному списку и **без пересечений**: один домен не должен быть
   одновременно в WG-группе и в `nuxk-*` (два маршрута — неопределённость).
   Порядок: группа `nuxk-*` → убрать домены из WG-группы → проверить →
   следующий список; WG-интерфейсы не трогать до конца миграции.
3. **Horizon трогает только объекты с префиксом `nuxk-`.** Чужие — никогда.
4. Агент проверяет версию KeeneticOS и отказывается работать на незнакомой
   (канал preview: API может меняться).
5. Десинк: nfqws2 со своими хостлистами; при возможности — ipset группы
   `nuxk-desync` как фильтр перед NFQUEUE (`connbytes 1:6`).
6. Сбой → роутер сам поднимает домен на ступень выше
   (напрямую → десинк → WARP → VLESS), Pi проверяет пробами и уточняет.
   Сигналы: автообучение nfqws2, пробы с Pi (DNS-сигналов в native-режиме нет).
7. Пробы с Pi по диапазонам исходных портов (40000–40099 → WARP,
   40100–40199 → VLESS, 40200–40299 → тестовый nfqws2) — через реальный WAN.
8. Отказ туннеля: в native-режиме — `auto` у `dns-proxy route` (проверить
   поведение); политика «без запасного пути» (напрямую или блок) — **не решена**.
9. IPv6: у роутера 2 глобальных адреса — проверить, как native-маршрутизация
   ведёт себя с AAAA (ip6tables DNSRT-правила в E0c).
10. Обновления: пакет решений с версией и ack; изменения групп пачкой.
11. Бюджет: агент ≤ 10 МБ (`GOMEMLIMIT=12MiB`, `GOGC=50`), CPU в покое ≈ 0.

Этапы: **E0** ✅ → **E0c** устройство встроенной маршрутизации → **E0b**
эксперимент с тестовой группой → **E1** агент (бэкенд `keenetic`) →
**E2** агент на роутере + перенос доменов из WG-списков в Horizon → **E3** сигналы и эскалация → **E4** Pi: пробы,
подбор, новый UI → **E5** xray/VLESS как OpkgTun1 (параллельно).

## Задача 2 — E0b: эксперимент с тестовой группой (каждый шаг — с согласия)

Меняет конфигурацию роутера. Перед каждым шагом покажи команду и откат,
выполняй только после «да». **Не сохранять** конфигурацию
(`system configuration save` не вызывать) — перезагрузка тоже откатит.

1. Создать группу `nuxk-e0test` с одним безобидным доменом, которого нет в
   других списках: `ifconfig.co` (отвечает и по IPv4, и по IPv6),

2. Маршрут `nuxk-e0test` → один из WG пользователя (спросить, какой можно).
   WG тут только временная цель теста: это единственный туннель, который
   прошивка уже видит как интерфейс. Проверяем механизм (группа → ipset →
   маршрут), а не WG — в итоговой схеме WG не будет.
3. С клиента LAN (лучше с самого Pi):
   - `nslookup ifconfig.co 192.168.2.1`, затем `curl -4 -s https://ifconfig.co`

   - `curl -6 -s https://ifconfig.co` → если показывает IPv6 провайдера, а не
     туннеля, — **утечка по IPv6 подтверждена**;
   - поддомены: `curl -4 -s https://api.ifconfig.co/ip` (если резолвится) —
     попал ли поддомен в тот же ipset без отдельного `include`;
   - запись в ipset появляется сразу после ответа DNS (до первого SYN).
4. Откат: удалить маршрут и группу (`no …`), убедиться, что ipset очистился
   и `ifconfig.me` снова идёт напрямую.
5. Отдельно (если есть `ipset`): проверка timeout —
   `ipset create nuxk_e0 hash:ip timeout 60 && ipset add nuxk_e0 192.0.2.1 && ipset list nuxk_e0; ipset destroy nuxk_e0`.

Прежний план E0b (логирующий DNS на Pi как upstream Keenetic) **отменён**:

## Задача 2b — E0d (каждый шаг — с согласия; конфиг не сохранять)

**Схема RCI (чтение И запись без авторизации с localhost подтверждены 25.09):**
запись — `POST /rci/` той же структурой, что отдаёт чтение; удаление —
`{"no": true}` на объекте; в ответе на каждое действие `status` с `code`
(`101581000` группа создана, `101582200` FQDN добавлен, `101581100` группа
удалена) — агент проверяет каждый шаг по ним. Пароль admin агенту не нужен.


```
GET /rci/object-group  → {"fqdn": {"<имя>": {"description": "...",
                           "include": [{"address": "openai.com"}, ...]}}, "ip": {...}}
GET /rci/dns-proxy     → {"route": [{"group": "<имя>", "interface": "Wireguard1",
                           "auto": true, "index": "<hash>", "comment": ""}],
                           "https": {...}, "filter": {"profile": {...}}}
```

У пользователя: `domain-list0` («AI», 49) и `domain-list1` («Meta», 23) →
оба на `Wireguard1`, `auto: true`. Это стартовые данные для импорта.

1. **Запись через RCI.** Пробуем ту же структуру, что отдаёт чтение (пустая
   группа без маршрута, сразу удалить):
   `curl -s -d '{"object-group":{"fqdn":{"nuxk-e0test":{"include":[{"address":"example.com"}]}}}}' http://127.0.0.1:79/rci/`,
   чтение `GET /rci/object-group/fqdn/nuxk-e0test`, удаление
   `{"object-group":{"fqdn":{"nuxk-e0test":{"no":true}}}}`. Если формат не
   принят — `{"parse":"<команда CLI>"}` с синтаксисом из E0b. Показать
   пользователю запрос и откат, затем:
   создать `object-group fqdn nuxk-e0test` с `include github.com` через
   `POST http://127.0.0.1:79/rci/` (JSON, запрос с самого роутера по SSH),
   прочитать его обратно (`/rci/show/running-config` или `object-group`),
   удалить тем же способом. Нужен ответ: принимает ли RCI запись с
   localhost без авторизации; точный формат JSON для группы и маршрута.
2. **Поддомены.** `github.com` уже в `domain-list0` — не годится. Группа
   `nuxk-e0test` только с `include example.com` + маршрут на `Wireguard1`.

   спрашивать): `nslookup www.example.com 192.168.2.1`. Если
   `_NDM_OGDN_4_@nuxk-e0test` после этого не пуст — поддомены покрываются

   https://ifconfig.co` отвечает IP туннеля. Откат: тот же `-D` вместо `-I`.
4. Удалить маршрут и группу, убедиться, что ipset'ы исчезли.

   - `curl -s -H "Authorization: Bearer $TOKEN" -d '{"groups":["domain-list0"],"mode":"vless"}' http://192.168.2.1:4141/api/v1/plane/import`;
   - `GET /api/v1/plane` → все 49 доменов в `conflicts` (они ещё в domain-list0),
     `pending` пуст — роутер не тронут.
5. Перенос одного домена (с согласия): `PLANE_APPLY="1"`, restart; в веб-
   интерфейсе Keenetic убрать из domain-list0 один домен, например
   `githubcopilot.com`. В течение минуты: группа `nuxk-vless` с ним,
   маршрут на `Wireguard1`, цепочка `ip6tables -S NUXK_V6_DENY` с двумя
   правилами. Проверить `dig @192.168.2.1 githubcopilot.com` → IP в
   `_NDM_OGDN_4_@nuxk-vless`; `curl -6 -m 5 https://githubcopilot.com` —
   отказ сразу.
6. Откат: `curl -X PUT -d '{"lists":[]}' …/api/v1/plane/lists` → группа,
   маршрут и правила v6 исчезают; вернуть домен в domain-list0;
   `PLANE_APPLY="0"`. Прислать облачной сессии `GET /api/v1/plane` до и после.

## Правила безопасности для этой сессии

- На роутере без явного согласия пользователя — только чтение.
- Не выполнять `opkg dns-override`, не трогать firewall/NAT, не
  перезапускать ndm, не сохранять конфигурацию Keenetic.
- Не трогать DNS-настройки пользователя (upstream, DoH/DoT, `DnsProfile0`) и
  его WG-списки/маршруты — только объекты с префиксом `nuxk-`.
- Никогда не выводить `show running-config` целиком — там учётные данные.
- Пароль Entware не записывать в файлы и команды; пусть `ssh` спросит сам.
