## Принятая архитектура (главное)

**Pi — «мозг» (control plane), роутер — «руки» (data plane).** На роутере только
движки (nfqws2, usque, xray) и маленький **nuxk-agent**; UI, кэш решений,
подбор стратегий, пресеты, история — на Pi. Pi выключен → роутер работает по
последнему пакету решений.

**Решение принимается в момент DNS, не при подключении.** После E0 (25.09)
выбран **native-режим**: nuxk ведёт встроенную маршрутизацию KeeneticOS по
доменам, а не строит свою.

```
Pi: решения домен → режим ──► nuxk-agent на роутере (RCI / ndmc)
   object-group fqdn nuxk-warp   ─► dns-proxy route ─► OpkgTun0 (usque)
   object-group fqdn nuxk-vless  ─► dns-proxy route ─► OpkgTun1 (xray)
   object-group fqdn nuxk-wg-*   ─► dns-proxy route ─► WireguardN
   object-group fqdn nuxk-desync ─► список для nfqws2 (маршрута нет)
ndnproxy + ядро сами: ipset, метки (_NDM_DNSRT_*), таблицы (4096+)
```

Почему (факты E0 на Ultra NC-1812, KeeneticOS 5.01 preview):
- у пользователя уже работает встроенная маршрутизация по доменам —
  4 WG-списка, `_NDM_DNSRT_PREROUTING_MANGLE`, таблицы 4096–4099;
- её правила перезаписывают метку целиком (`--set-xmark …/0xffffffff`) —
  своих бит для меток фактически нет, а в native-режиме метки выделяет Keenetic;
- на :53 `ndnproxy` с DoH (Google, Cloudflare) и профилем `DnsProfile0`
  (xbox-dns) — DNS пользователя **не трогаем**; «мягкий режим» с агентом на
  `127.0.0.1:5300` отменён, остаётся только для бэкенда `linux`.

Решения по дизайну:
1. **Два бэкенда агента, один интерфейс для Pi:** `keenetic` (объекты ndm) —
   основной; `linux` (свой резолвер + ipset + свои метки) — стенд на Pi и
   роутеры без этой функции.
2. **WG — ещё одна цель маршрута** (как WARP и VLESS). Сейчас WG-списки
   пользователь ведёт руками; дальше ими управляет Horizon: импорт как
   решения с источником «вручную», затем миграция без простоя — создать
   `nuxk-*` копии, проверить, выключить старые (не удалять сразу).
3. **Horizon трогает только объекты с префиксом `nuxk-`.** Чужие — никогда.
4. Агент проверяет версию KeeneticOS и отказывается работать на незнакомой
   (канал preview: API может меняться).
5. Десинк: nfqws2 со своими хостлистами; при возможности — ipset группы
   `nuxk-desync` как фильтр перед NFQUEUE (`connbytes 1:6`).
6. Сбой → роутер сам поднимает домен на ступень выше
   (напрямую → десинк → WARP → VLESS/WG), Pi проверяет пробами и уточняет.
   Сигналы: автообучение nfqws2, пробы с Pi (DNS-сигналов в native-режиме нет).
7. Пробы с Pi по диапазонам исходных портов (40000–40099 → WARP,
   40100–40199 → VLESS, 40200–40299 → тестовый nfqws2) — через реальный WAN.
8. Отказ туннеля: в native-режиме — `auto` у `dns-proxy route` (проверить
   поведение); политика «без запасного пути» (напрямую или блок) — **не решена**.
9. IPv6: у роутера 2 глобальных адреса — проверить, как native-маршрутизация
   ведёт себя с AAAA (ip6tables DNSRT-правила в E0c).
10. Обновления: пакет решений с версией и ack; изменения групп пачкой.
11. Бюджет: агент ≤ 10 МБ (`GOMEMLIMIT=12MiB`, `GOGC=50`), CPU в покое ≈ 0.

Этапы: **E0** ✅ → **E0c** устройство встроенной маршрутизации → **E0b**
эксперимент с тестовой группой → **E1** агент (бэкенд `keenetic`) →
**E2** миграция WG-списков → **E3** сигналы и эскалация → **E4** Pi: пробы,
подбор, новый UI → **E5** xray/VLESS как OpkgTun1 (параллельно).

## Задача 1 — E0: проверка роутера (только чтение) — ✅ выполнена 24.09

```sh
cd ~/nuxk-horizon && git pull
sh tools/e0/run.sh 192.168.2.1 222
```

Скрипт спросит пароль Entware (или возьмёт SSH-ключ), выполнит на роутере
`tools/e0/router-check.sh` и сохранит `e0-report-<ip>-<дата>.txt`. Ничего не
меняет: только `show`, списки, чтение `/proc`, справка CLI.

Разбери блок SUMMARY для пользователя:

| Ключ | Что значит для дизайна |
|---|---|
| `mark_bit28`, `mark_bit31` | `free` у обоих → два туннеля на битах 28/31. Если 31 занят — ищем другой селектор, сообщить |
| `dns53`, `dns_override`, `dns_upstreams`, `dns_proxy_encrypted` | кто держит :53, какие upstream; встроенный DoT/DoH Keenetic в мягком режиме надо выключить |
| раздел «CLI syntax for ip name-server» | принимает ли `ip name-server` адрес с портом — основа мягкого режима |
| `match_*`, `target_*`, `kmod_*`, `ipset` | есть ли set/connbytes/connmark/NFQUEUE/NFLOG; `ipset 0` → инсталлятор его ставит |
| `ppe`, `offload_modules` | аппаратное ускорение: наш дизайн трогает только новые соединения — отметить, включено ли |
| `tables_in_use` | свободные номера таблиц маршрутизации для режимов |
| `has_*`, `init_scripts` | не стоят ли уже HydraRoute, xkeen, AdGuardHome, dnsmasq — конфликт за DNS/метки |
| `ipv6_global` | есть ли глобальный IPv6 (важно для AAAA-политики) |

Полный отчёт содержит устройство LAN — в git его не клади (`e0-report-*.txt`
в `.gitignore`).

## Задача 1b — E0c: устройство встроенной маршрутизации (только чтение)

```sh
cd ~/nuxk-horizon && git pull
sh tools/e0/run.sh 192.168.2.1 222 keenetic-dnsrt.sh
```

Скрипт `tools/e0/keenetic-dnsrt.sh` показывает: доступен ли RCI
(`127.0.0.1:79`), имена и размеры `object-group fqdn`, одну группу целиком
(синтаксис), формы записей (домен / `*.` / IP / CIDR), строки `route
object-group` в `dns-proxy`, интерфейсы-цели, ipset'ы DNSRT (тип, число
записей, timeout), правила DNSRT в iptables v4/v6, порядок в mangle
PREROUTING, fwmark → таблица, и что такое `S99aiway-manager`.

Для пользователя ответь на вопросы:
- точный синтаксис группы и маршрута (для генератора в агенте);
- лимиты: сколько записей в самой большой группе, есть ли ошибки/предупреждения;
- поддомены: нужны ли `*.` или домен покрывает поддомены сам;
- что значит `auto` в маршруте и что происходит при падении WG;
- есть ли DNSRT-правила для IPv6;
- виден ли `OpkgTun0` прошивке (если usque не стоит — просто «нет»);
- `aiway-manager`: что это и трогает ли DNS/маршрутизацию.

## Задача 2 — E0b: эксперимент с тестовой группой (каждый шаг — с согласия)

Меняет конфигурацию роутера. Перед каждым шагом покажи команду и откат,
выполняй только после «да». **Не сохранять** конфигурацию
(`system configuration save` не вызывать) — перезагрузка тоже откатит.

1. Создать группу `nuxk-e0test` с одним безобидным доменом, которого нет в
   других списках (например `ifconfig.me`), синтаксисом из E0c.
2. Маршрут `nuxk-e0test` → один из WG пользователя (спросить, какой можно).
3. С клиента LAN: `nslookup ifconfig.me 192.168.2.1`, затем `curl ifconfig.me`.
   Проверить: IP домена появился в ipset DNSRT; внешний IP = выход WG;
   сколько прошло от ответа DNS до появления записи (должно быть «сразу»).
4. Откат: удалить маршрут и группу (`no …`), убедиться, что ipset очистился
   и `ifconfig.me` снова идёт напрямую.
5. Отдельно (если есть `ipset`): проверка timeout —
   `ipset create nuxk_e0 hash:ip timeout 60 && ipset add nuxk_e0 192.0.2.1 && ipset list nuxk_e0; ipset destroy nuxk_e0`.

Прежний план E0b (логирующий DNS на Pi как upstream Keenetic) **отменён**:
DNS пользователя не трогаем.

## Правила безопасности для этой сессии

- На роутере без явного согласия пользователя — только чтение.
- Не выполнять `opkg dns-override`, не трогать firewall/NAT, не
  перезапускать ndm, не сохранять конфигурацию Keenetic.
- Не трогать DNS-настройки пользователя (upstream, DoH/DoT, `DnsProfile0`) и
  его WG-списки/маршруты — только объекты с префиксом `nuxk-`.
- Никогда не выводить `show running-config` целиком — там учётные данные.
- Пароль Entware не записывать в файлы и команды; пусть `ssh` спросит сам.
