## Принятая архитектура (главное)

**Pi — «мозг» (control plane), роутер — «руки» (data plane).** На роутере только
движки (nfqws2, usque, xray) и маленький **nuxk-agent**; UI, кэш решений,
подбор стратегий, пресеты, история — на Pi. Pi выключен → роутер работает по
последнему пакету решений.

**Решение принимается в момент DNS, не при подключении:**

```
клиенты ─► Keenetic DNS (:53) ─► nuxk-agent (127.0.0.1:5300) ─► DoH через туннель
                                      │
                                      └─ ДО ответа: IP → ipset (nuxk_desync / nuxk_warp / nuxk_vless)
SYN ─► mangle: ctstate NEW → match-set → CONNMARK; остальные → restore-mark
     ─► ip rule fwmark → таблица режима → opkgtun0 / tun-xray / WAN
     ─► nuxk_desync (+ nuxk_unknown) и первые ~6 пакетов → NFQUEUE → nfqws2
```

Решения по дизайну:
1. **Мягкий DNS-режим (выбран пользователем):** порт 53 остаётся у Keenetic,
   агент — его единственный upstream на `127.0.0.1:5300` (не 5353: его
   занимает mDNS). `opkg dns-override` —
   только запасной «полный режим».
2. Агент отдаёт TTL ≤ 300 с, записи ipset живут часы и продлеваются при
   запросе (кэш Keenetic всегда истекает раньше записи в наборе).
3. Свой агент вместо форка HydraRoute (`nuxk-plane/README.md` — справочник).
4. Метки: бит 28 (`0x10000000`) — свободен по документации; для второго
   туннеля нужен ещё бит — кандидат 31 (`0x80000000`), **проверить в E0**.
   Биты 29/30 — nfqws2 (исключение/обработанный пакет).
5. NFQUEUE только для `nuxk_desync` и `nuxk_unknown` (новые домены на 10 мин,
   автообучение nfqws2 как детектор сбоев), `connbytes 1:6`.
6. Сбой → роутер сам поднимает домен на ступень выше
   (напрямую → десинк → WARP → VLESS), Pi проверяет пробами и уточняет.
7. Пробы с Pi по диапазонам исходных портов (40000–40099 → WARP,
   40100–40199 → VLESS, 40200–40299 → тестовый nfqws2) — через реальный WAN
   роутера, не трогая пользователей.
8. Отказ туннеля → `ip route replace` в таблице режима на запасной путь;
   политика «без запасного пути» (напрямую или блок) — **не решена**.
9. Для доменов с особым режимом: без AAAA, UDP 443 отклонять при десинке без
   QUIC-стратегии; перенаправление :53, блок :853, NXDOMAIN на
   `use-application-dns.net`.
10. Обновления атомарные (`ipset swap`), пакеты решений с версией и ack.
11. Бюджет: агент ≤ 10 МБ (`GOMEMLIMIT=12MiB`, `GOGC=50`), CPU в покое ≈ 0.

Этапы: **E0** проверка роутера → **E1** агент на стенде Pi (замеры dnsperf,
iperf3) → **E2** агент на роутере → **E3** сигналы и эскалация → **E4** Pi:
пробы, подбор, пакеты решений, новый UI → **E5** xray/VLESS (параллельно).

## Задача 1 — E0: проверка роутера (только чтение)

```sh
cd ~/nuxk-horizon && git pull
sh tools/e0/run.sh 192.168.2.1 222
```

Скрипт спросит пароль Entware (или возьмёт SSH-ключ), выполнит на роутере
`tools/e0/router-check.sh` и сохранит `e0-report-<ip>-<дата>.txt`. Ничего не
меняет: только `show`, списки, чтение `/proc`, справка CLI.

Разбери блок SUMMARY для пользователя:

| Ключ | Что значит для дизайна |
|---|---|
| `mark_bit28`, `mark_bit31` | `free` у обоих → два туннеля на битах 28/31. Если 31 занят — ищем другой селектор, сообщить |
| `dns53`, `dns_override`, `dns_upstreams`, `dns_proxy_encrypted` | кто держит :53, какие upstream; встроенный DoT/DoH Keenetic в мягком режиме надо выключить |
| раздел «CLI syntax for ip name-server» | принимает ли `ip name-server` адрес с портом — основа мягкого режима |
| `match_*`, `target_*`, `kmod_*`, `ipset` | есть ли set/connbytes/connmark/NFQUEUE/NFLOG; `ipset 0` → инсталлятор его ставит |
| `ppe`, `offload_modules` | аппаратное ускорение: наш дизайн трогает только новые соединения — отметить, включено ли |
| `tables_in_use` | свободные номера таблиц маршрутизации для режимов |
| `has_*`, `init_scripts` | не стоят ли уже HydraRoute, xkeen, AdGuardHome, dnsmasq — конфликт за DNS/метки |
| `ipv6_global` | есть ли глобальный IPv6 (важно для AAAA-политики) |

Полный отчёт содержит устройство LAN — в git его не клади (`e0-report-*.txt`
в `.gitignore`).

## Задача 2 — E0b: проверки с изменениями (каждый шаг — с согласия пользователя)

Эти проверки временно меняют настройки роутера. Перед каждым шагом покажи
пользователю команду и команду отката, выполняй только после «да».
Конфигурацию Keenetic **не сохраняй** (`system configuration save` не
вызывать) — тогда перезагрузка роутера тоже откатывает изменения.

1. **Логирующий DNS на Pi** (на роутер ничего не ставится):
   ```sh
   docker run --rm -d --name e0dns -p 192.168.2.10:5300:5300/udp -p 192.168.2.10:5300:5300/tcp \
     alpine sh -c 'apk add --no-cache dnsmasq >/dev/null && exec dnsmasq -k -p 5300 \
       --log-queries --log-facility=- --no-resolv --server=1.1.1.1 --max-ttl=60'
   docker logs -f e0dns
   ```
2. **Upstream с портом.** Точный синтаксис сначала сверь со справкой из отчёта
   E0. Ожидаемо (проверить!):
   `ssh -p 222 root@192.168.2.1 "ndmc -c 'ip name-server 192.168.2.10:5300'"`.
   Откат: та же команда с `no` в начале. Запиши, какой синтаксис принят.
3. **Порядок upstream.** Оставь один старый upstream и добавленный. С
   клиента в LAN 20–30 запросов разных имён — какая доля пришла в лог
   `e0dns`? Все → строгий порядок; часть → параллельно/round-robin
   (тогда агент обязан быть единственным upstream).
4. **Кэш и TTL.** С клиента каждые 20 с спрашивать одно имя 3 минуты. При
   `--max-ttl=60` в логе должен быть повторный запрос примерно раз в минуту.
   Если реже — Keenetic держит свой минимальный TTL, записать какой.
5. **AAAA.** `nslookup -type=AAAA youtube.com 192.168.2.1` с клиента — дошёл
   ли AAAA-запрос до `e0dns`.
6. **ipset с timeout** (если `ipset 1`):
   ```sh
   ipset create nuxk_e0 hash:ip timeout 60 && ipset add nuxk_e0 192.0.2.1 && ipset list nuxk_e0; ipset destroy nuxk_e0
   ```
7. Откатить upstream, `docker rm -f e0dns`, показать итог.

## Правила безопасности для этой сессии

- На роутере без явного согласия пользователя — только чтение.
- Не выполнять `opkg dns-override`, не трогать firewall/NAT, не
  перезапускать ndm, не сохранять конфигурацию Keenetic.
- Никогда не выводить `show running-config` целиком — там учётные данные.
- Пароль Entware не записывать в файлы и команды; пусть `ssh` спросит сам.
