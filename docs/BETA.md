# nuxk 0.2.0-beta.3 — установка и тест на роутере

Бета состоит из трёх частей:

| Где | Что | Как ставится |
|---|---|---|
| **Роутер Keenetic** | агент `nuxk-core`: nfqws2, WARP (по желанию), списки DPI / WARP / VLESS, лёгкий веб | форма инсталлятора |
| **Raspberry Pi 5** (192.168.2.10) | **инсталлятор** (:4300), **контроллер** с полным вебом (:4200), тестовый стенд (:4242) | `deploy/pi/bootstrap.sh` |
| контракт между ними | `nuxk-core/api/openapi.yaml` — REST + события SSE; человек входит по паролю, контроллер — по ключу роутера | — |

Роутер работает и без Pi: списки и намерения хранятся на нём.
Стенд на :4242 — это Docker на Pi, **не роутер**. Интерфейс теперь пишет это прямо
(«Стенд Pi (Docker)»), чтобы данные стенда не путались с роутерными.

Ставим **по этапам**. На каждом этапе есть проверка и откат; следующий этап — только если
предыдущий в порядке. До этапа 5 nuxk **не меняет маршрутизацию** роутера.

---

## Этап 0. Подготовка роутера (один раз, руками)

1. **Резервная копия конфигурации Keenetic.** «Управление → Параметры системы →
   Файлы» → скачайте `startup-config`. Это откат на крайний случай.
2. **Компоненты** («Управление → Параметры системы → Изменить набор компонентов»),
   роутер перезагрузится:
   - «Поддержка открытых пакетов OPKG»;
   - «Модули ядра подсистемы Netfilter» — без них nfqws2 не запустится;
   - «Протокол IPv6».
3. **Entware** (если ещё нет) — по инструкции Keenetic, на USB (ext4) или во
   внутреннюю память. SSH Entware: по умолчанию **порт 222**, `root` / `keenetic`.
   На роутере в квартире Entware слушает **порт 22**.
4. **Смените пароль Entware**: `ssh root@<роутер> -p <порт>` → `passwd`.
5. **Время**: «Дата и время» → синхронизация (NTP).

## Этап 1. Pi: инсталлятор и контроллер

```sh
cd ~/nuxk-horizon
git pull                     # или NUXK_REF=v0.2.0-beta.3 sh deploy/pi/bootstrap.sh
sh deploy/pi/bootstrap.sh
```

Скрипт проверит Pi, соберёт образы (первый раз 5–10 минут) и напечатает адреса и код
доступа инсталлятора. Контроллер пока выключен — он включается на этапе 3, когда
на роутере будет агент.

## Этап 2. Установка на роутер

1. Откройте **http://192.168.2.10:4300**, кнопка «Квартира · 192.168.2.1» (порт 22
   подставится сам) или свой адрес и порт, `root`, пароль Entware, код доступа.
2. **«Проверить роутер»** — только чтение. Сверьте ключ SSH роутера над таблицей.
3. Отметьте шаги. По умолчанию отмечено всё, кроме WARP:
   - пакеты `curl`, `ca-certificates`, `ipset`;
   - `nfqws2-keenetic` из его репозитория. **Внимание:** штатный nfqws2 сразу
     начинает обрабатывать трафик по своему конфигу. Если что-то перестало
     открываться: `/opt/etc/init.d/S51nfqws2 stop`;
   - nuxk-core, init-скрипт, адаптер nfqws2, веб;
   - **usque (WARP) — по желанию.** Отметка = согласие с условиями Cloudflare WARP,
     создание интерфейса OpkgTun и сохранение конфигурации роутера. Перед
     установкой `cloudflareclient.com` добавляется в список nfqws2 (ваши записи
     остаются);
   - `nuxk.conf` (0600): адрес только в LAN, ключ для контроллера (`API_TOKEN` —
     копировать его никуда не нужно), **режим плана** (`PLANE_APPLY="0"`);
   - запуск и проверка `/api/v1/healthz`.
4. «Установить выбранное». В конце — адрес панели роутера и контроллера. Вход в панель
   роутера — **логин `root` и пароль Entware** (те же, что для SSH).

При первом запуске текущий `user.list` nfqws2 переносится в список «DPI» nuxk — ничего
не теряется. Пока в nuxk нет ни одного списка DPI, nuxk этот файл не трогает.

**Проверка этапа:**
- `http://<роутер>:4141` → `root` и пароль Entware → «Дашборд»: в шапке «Роутер …»,
  графики WAN через 10–20 секунд, карточка nfqws2 «работает» (или «частично», если
  его проба не проходит — причина написана под карточкой).
- После 5 неверных паролей подряд вход с этого адреса ненадолго блокируется (от 30 с,
  растёт до 15 мин) — это защита от подбора.
- На роутере: `/opt/etc/init.d/S99nuxk-core status`, лог `tail -f /opt/var/log/nuxk-core.log`.
- Интернет у всех устройств работает как раньше.

**Откат этапа:** `/opt/etc/init.d/S99nuxk-core stop` — nuxk останавливается, роутер
работает как до установки (плюс штатный nfqws2, его останавливает `S51nfqws2 stop`).

## Этап 3. Контроллер на Pi

В `deploy/pi/.env` раскомментируйте `COMPOSE_PROFILES=controller`, затем:

```sh
docker compose -f deploy/pi/docker-compose.yml up -d --build controller
```

Откройте **http://192.168.2.10:4200** — запустится мастер настройки:

1. **Пароль** — задайте пароль администратора панели (логин `admin`, не короче 8
   символов). На Pi хранится только его хеш.
2. **Роутер** — адрес роутера (подставлен по адресу Pi, проверьте), логин `root` и
   пароль Entware. Роутер проверит их и выдаст контроллеру свой ключ доступа; сам
   пароль root нигде не сохраняется.
3. **Готово** — модель роутера и версия nuxk-core → «Открыть панель».

В «Системе» — «через контроллер Pi», связь «есть»; графики хранят час истории. Там же
«Сменить роутер» (снова шаг 2) и «Выйти». Настройки лежат в томе контроллера
(`controller.json`); если пароль администратора забыт — удалите этот файл
и пройдите мастер заново:

```sh
docker compose -f deploy/pi/docker-compose.yml rm -sf controller
docker volume rm nuxk-pi_controller-data
docker compose -f deploy/pi/docker-compose.yml up -d controller
```

> Если в `.env` уже заданы `AGENT_URL` и `AGENT_TOKEN` (старая настройка), контроллер
> возьмёт роутер оттуда и шаг 2 пропустит.

> Мастер открыт для первого, кто зайдёт на свежий контроллер: пройдите его сразу после
> запуска.

> Pi стоит в сети квартиры (192.168.2.0/24). Роутер дома (192.168.1.1) ему не виден —
> для него контроллер запускается в домашней сети (Docker-хост 192.168.1.100) или
> используется лёгкий веб прямо с роутера.

## Этап 3б. Подбор стратегий (плагин GP)

Только в полной версии — через контроллер на Pi. Лёгкий веб на роутере этих вкладок не
показывает, и на роутер плагины не ставятся никогда.

«Плагины» → GP → «Установить». Контроллер скачает на Pi ядро GP, Python-зависимости и
zapret2 (около минуты), запустит его отдельным процессом с сетевыми правами только внутри
контейнера и сменит его заводской пароль. Потом:

- **«Прогоны»** — выберите домены (список nuxk или свои), глубину («быстро» — до первой
  рабочей стратегии) и что проверять. Прогон может идти часами; найденное сохраняется,
  даже если остановить.
- **«Стратегии»** — что нашлось. «На роутер…» покажет, что изменится, и после
  подтверждения добавит стратегию профилем nfqws2 только для выбранных доменов
  (`NFQWS_ARGS_CUSTOM`, копия `nfqws2.conf.nuxk-bak`, перезапуск nfqws2 на 1–2 с; если
  он не поднимется — конфиг вернётся сам). «Убрать» — обратно.

> Проверка идёт с Pi через роутер. Для доменов, уже стоящих в списке DPI роутера, nfqws2
> роутера накладывает свою стратегию на проверяемую — для точных результатов исключите Pi
> из nfqws2 на роутере: политика подключения Keenetic с именем `nfqws` и
> `POLICY_EXCLUDE=1` в `/opt/etc/nfqws2/nfqws2.conf` (это изменение роутера — вручную).

## Этап 4. Списки в режиме плана

«Списки»: DPI / WARP / VLESS. Можно импортировать ваши списки Keenetic («Ваши списки в
Keenetic» → WARP). Сохраните и посмотрите блок «План»: что nuxk сделал бы на роутере.
В режиме плана **ничего не меняется**.

- Домены, которые ещё есть в ваших старых списках Keenetic, стоят в «Конфликтах» —
  nuxk их не трогает, пока вы не уберёте их из старого списка.
- «Туннель упал: напрямую / блокировать» — что делать с сайтами WARP/VLESS при падении
  туннеля. Режим «блокировать» на железе ещё не проверен — начните с «напрямую».

## Этап 5. Применение — начните с одного домена

1. Оставьте в «Списках» **один** тестовый домен (например, в WARP).
2. На роутере: `PLANE_APPLY="1"` в `/opt/etc/nuxk/nuxk.conf`, затем
   `/opt/etc/init.d/S99nuxk-core restart`.
3. Через минуту в «Списках» → «Роутер»: «применяется», план пуст, ошибок нет.
   В веб-интерфейсе Keenetic появится список `nuxk-warp` с маршрутом.
4. Откройте домен с устройства; выход должен быть через WARP (например,
   `https://www.cloudflare.com/cdn-cgi/trace` показывает `warp=on`, если домен в списке).
5. Только потом переносите остальные домены.

**Откат этапа 5** (в порядке строгости):
- удалите списки в «Списках» и сохраните — nuxk сам уберёт свои `nuxk-*` объекты;
- `PLANE_APPLY="0"` + рестарт — nuxk перестаёт менять роутер (объекты остаются);
- вручную на роутере:
  ```sh
  curl -s -X POST http://127.0.0.1:79/rci/ -d '{"dns-proxy":{"route":{"group":"nuxk-warp","interface":"OpkgTun0","no":true}}}'
  curl -s -X POST http://127.0.0.1:79/rci/ -d '{"object-group":{"fqdn":{"nuxk-warp":{"no":true}}}}'
  ip6tables -D FORWARD -j NUXK_V6_DENY; ip6tables -F NUXK_V6_DENY; ip6tables -X NUXK_V6_DENY
  ```
  (то же для `nuxk-vless` / `OpkgTun1`). Ваши собственные списки и маршруты nuxk
  не трогает никогда.

## Полное удаление

```sh
/opt/etc/init.d/S99nuxk-core stop
rm -f /opt/usr/bin/nuxk-core* /opt/etc/init.d/S99nuxk-core
rm -rf /opt/etc/nuxk /opt/share/www/nuxk /opt/var/log/nuxk-core.*
# если ставили инсталлятором:
opkg remove usque-keenetic
opkg remove nfqws2-keenetic && rm -f /opt/etc/opkg/nfqws2-keenetic.conf
```

Прошлая версия nuxk-core: `mv /opt/usr/bin/nuxk-core.prev /opt/usr/bin/nuxk-core` и рестарт.

## Что проверено до релиза и что нет

- **Проверено:** юнит-тесты и `-race`; сквозной тест инсталлятора через настоящий SSH
  на имитации роутера (включая WARP и перенос `user.list`); плоскость на имитации RCI
  с реальными ответами прошивки; контракт OpenAPI против маршрутов агента; контроллер
  (прокси, токены, история, SSE, падение агента); веб в браузере через агент и через
  контроллер, светлая/тёмная тема, телефон. Сборка ipk usque под mips/mipsel/aarch64.
- **Проверено для подбора (0.2.0-beta.3):** хост плагинов в контейнере контроллера на Pi
  (плагин не читает секреты контроллера и его память); настоящий прогон GP с Pi;
  применение, откат и «Убрать» — через панель на настоящем агенте с имитацией nfqws2 и
  заводским `nfqws2.conf` nfqws2-keenetic.
- **Исправлено по аудиту перед роутером:** зависание вызова init-скрипта, если демон
  держит его вывод; запись состояния с fsync (пропадание питания не оставит пустой
  файл); `/status` больше не ждёт медленную синхронизацию с прошивкой; лог ротируется
  сам (2 × 512 КиБ); лимит тела запроса и защитные заголовки веба.
- **Не проверено на железе:** этапы 4–5 на настоящем Keenetic, режим «блокировать»,
  применение стратегии GP на настоящем роутере. Если что-то упадёт —
  пришлите вывод формы, `tail -50 /opt/var/log/nuxk-core.log` и
  `cat /opt/var/log/nuxk-core.crash`.
